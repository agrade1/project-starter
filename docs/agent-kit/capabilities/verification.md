# 테스트 · 브라우저 · 사용자 흐름 검증

## 목적과 사용 시점

완료 주장에 실제 관측 증거를 붙일 때 사용한다.

## 입력과 부족한 정보

- 필수: 수용 기준·변경 diff·검사 환경·허용된 명령
- 선택: 기존 test/build/lint·브라우저·안전한 테스트 데이터
- 부족하면: 환경이 없으면 실행 불가 사유와 정확한 수동 절차를 남긴다. 임의 설치·유료 호출·운영 데이터 사용은 하지 않는다.
- 공통 경계: [작업 규칙](../common/WORKING_RULES.md). 프로젝트 경로표를 따라 기존 정본을 쓴다.

## 실행 단계

1. 기준마다 코드/문서/단위/통합/브라우저/사람 확인 중 필요한 증거를 정한다. 관련 없는 전체 suite나 live 실험을 반복하지 않는다.
2. 기존 검사 명령을 확인하고 실제 실행 명령·환경·대상 HEAD·exit code·출력 위치를 기록한다. mock과 local/live 결과를 구별한다.
3. 화면 변경은 실제 앱에서 핵심 행동과 빈 결과·오류 복구를 확인한다. 키보드·focus·label·좁은 화면을 검사하고 필요 시 콘솔/네트워크 오류를 본다. 클릭 후 최신 화면을 다시 확인한다.
4. 보안/데이터/동시성 변경은 거부 경로·회귀·해당 경합 조건을 검증한다. 배타 자원 검사는 순차로 돌린다.
5. 통합된 최종 상태에서 프로젝트가 요구하는 검사 한 번을 수행한다. 코드 변경이 없으면 문서 링크/예시 검사로 한정한다.
6. 관측 결과가 예상과 다르면 실패 원인을 분류한다. 녹색 테스트가 빈 입력·assert 누락·검사 0회 때문인지도 확인한다.

## 산출물

[REVIEW 양식](../templates/REVIEW.md)의 시나리오별 검사 표. 로컬 스크린샷/로그 경로와 수동 절차를 기록한다.

## 검증과 완료

필수 시나리오가 관측되고 A가 없으며 미검증을 숨기지 않아야 완료다. 테스트 통과가 사업 검증·출시 승인을 대신하지 않는다.

## 실패·보류·사람 확인

코드 결함은 구현자로, 자료 부족은 조사자로, 사람 실물 실험은 사람에게 넘긴다. 미실행 검사를 통과로 바꾸지 않는다.

## 다음 단계와 인계

독립 리뷰와 통합 담당에게 실제 결과·실패 재현·증거·미검증 범위를 넘긴다.

## 작은 작업에서 생략

문서 변경은 링크·예시 확인만, 사소한 코드 변경은 해당 focused 검사부터 한다. 새 테스트 프레임워크나 무관한 stress 검사를 추가하지 않는다.

## 킷 문서 검사 도구

Python 3.9 이상이 이미 있으면 [check-links.py](check-links.py)를 실행한다. 패키지 안의 상대 Markdown 파일 링크와 역할 10항목/기능 필수 절을 검사한다.

```sh
python3 docs/agent-kit/capabilities/check-links.py
python3 docs/agent-kit/capabilities/check-links.py --self-test
```

외부 URL 접근·모든 Markdown 문법·서술의 진실성은 자동 검사하지 않는다. 없는 파일/anchor와 패키지 밖 링크는 실패한다. 인라인 코드 속 프로젝트 산출물 경로는 템플릿 자리이므로 실제 프로젝트의 경로표로 별도 확인한다. [작은 기능 예시](../examples/favorite-filter.md)로 역할 간 인계를 수동 추적한다.

## 선택 검사 도구의 유지보수

| 항목·등급 | 심각도·확률 | 영향 반경 | 유예 비용 | 수정 공수 | 기한·트리거 | 담당 | 근거·상태 |
|---|---|---|---|---|---|---|---|
| 토큰 린트의 빈 입력 통과 · B | P2 · 빈 토큰/잘못된 source 경로이면 재현 가능 | 선택 token-lint 사용자 | 현재 수동 입력/파일 수 확인으로 낮음 | 작은 입력 guard·회귀 검사 | CI 단독 완료 gate로 채택하기 전 검사 수/입력 유효성을 강제해야 함 | 대상 프로젝트 검증 담당 | token-lint.mjs는 빈 토큰·0파일도 exit 0 가능; 보조 검사로만 사용 |
| 필수 파일 목록 자동 보장 없음 · C | P3 · 파일과 모든 유입 링크를 함께 삭제할 때 낮은 확률 | 킷 구성 누락 | 수동 구성 확인으로 낮음 | 필요 시 짧은 필수 파일 목록 검사 | 다음 킷 파일 구조 변경 시 역할 8·기능 9·워크플로 4·양식 7을 확인하고 자동화 여부 판단 | 킷 유지보수 담당 | check-links.py는 현재 링크·존재 파일의 절을 검사; 자동 inventory 검사는 보류 |

파일 하나만 삭제하면 남은 링크가 오류를 잡는다. 파일과 연결 링크를 모두 지우는 구조 변경은 수동 구성 확인을 함께 한다. 토큰 린트의 사용 범위는 [디자인 지침](design.md)을 따른다.
