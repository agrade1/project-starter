# 사업 가설 · MVP · PRD

## 목적과 사용 시점

아이디어를 검증 가능한 문제와 가장 작은 제품 범위로 바꿀 때 사용한다. 사업성 판단 보조와 검증용 구현 허가를 분리한다.

## 입력과 부족한 정보

- 필수: 사용자 문제·대상·원하는 결과·이번 승인 범위
- 선택: 리서치·기존 사용 데이터·예산·일정·기존 PRD
- 부족하면: 목표·데이터 사용·승인 경계가 불명확하면 질문한다. 나머지는 가정과 변경 조건을 명시한 초안으로 진행한다.
- 공통 경계: [작업 규칙](../common/WORKING_RULES.md). 프로젝트 경로표를 따라 기존 정본을 쓴다.

## 실행 단계

1. 누가 어떤 상황에서 어떤 대안 대신 사용할지 한 문장으로 정리한다.
2. 근거와 가정을 나누고 가장 위험한 가설 하나를 선택한다. 사람이 해야 할 인터뷰·실물 실험에는 담당·시간·성공/실패 기준을 붙인다.
3. 핵심 사용자 흐름 하나를 정하고 필수/후속/제외 기능을 비용과 학습 가치로 나눈다. 사업 판단은 진행·축소·실험·보류 중 추천과 이유로 제시한다.
4. 기능마다 행동 → 관측 결과 형태의 수용 기준과 실패·복구 상태를 쓴다. MVP 이후 기능을 구현 목록에 섞지 않는다.
5. 사람에게 제품 개발 또는 제한된 프로토타입 중 어느 범위가 승인됐는지 확인한다. 이미 명시된 승인은 재질문하지 않는다.

## 산출물

[PROJECT 양식](../templates/PROJECT.md)의 문제·근거·MVP·수용 기준·결정. 별도 PRD가 있으면 그 문서만 갱신한다.

## 검증과 완료

필수 기능이 한 사용자 흐름으로 이어지고 각 기준을 관찰할 수 있어야 한다. 미확인 가설과 사람이 확인한 사실을 다른 상태로 표시했는지 검사한다.

## 실패·보류·사람 확인

필수 근거가 없으면 사업 검증 완료로 적지 않는다. 가설이 남아도 사용자가 승인한 제한된 실험은 진행할 수 있다. 비용·제품 방향·출시는 사람이 결정한다.

## 다음 단계와 인계

UX·UI에 흐름·대상·수용 기준, 기술 설계에 범위·데이터 제약, 기획·진행에 승인·미확인 실험을 전달한다.

## 작은 작업에서 생략

기존 PRD의 한 절에 변경 목표·제외·수용 기준을 적으면 충분하다. 시장 보고서·독립 CEO 세션을 의무화하지 않는다.
