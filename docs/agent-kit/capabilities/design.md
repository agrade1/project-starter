# 사용자 흐름 · 비주얼 · 디자인 시스템

## 목적과 사용 시점

새 화면 또는 기존 UI 변경의 동작과 시각적 계약을 구현자에게 넘길 때 사용한다.

## 입력과 부족한 정보

- 필수: 대상·핵심 흐름·수용 기준·기존 UI/컴포넌트·구현 제약
- 선택: 브랜드·레퍼런스·토큰·지원 화면 크기·접근성 목표
- 부족하면: 브랜드가 없으면 기존 UI를 기본안으로 삼고 선택 이유를 표시한다. 데이터/API가 미확정이면 임의로 확정하지 말고 계약 담당에게 질문한다.
- 공통 경계: [작업 규칙](../common/WORKING_RULES.md). 프로젝트 경로표를 따라 기존 정본을 쓴다.

## 실행 단계

1. 기존 화면과 컴포넌트를 읽고 진입→행동→결과→복구 흐름을 정한다. 각 화면의 기본·빈 결과·로딩·오류·성공·권한 없음·비활성 중 적용되는 상태를 작성한다.
2. 비주얼 방향이 필요하면 소수 레퍼런스의 URL·확인일·차용할 원칙을 남긴다. 이미지·로고 자체의 사용권을 추정하지 않는다.
3. 정보 위계·폰트·여백·색·반응형·모션을 정한다. 기존 토큰을 우선하며 필요하면 primitive(원시값)→semantic(의미)→component(사용처)로 연결한다.
4. 컴포넌트마다 variant·상태·데이터·label·키보드·focus·오류 안내를 연결한다. 화면별 핵심 메시지·주요 행동 버튼(CTA)·입력 예시·빈 상태·오류 복구 문구를 작성한다. 결과의 출처·한계와 샘플/베타 여부는 실제 사실에 맞게 표시한다. 단일 CSS 변수로 충분한 작은 UI에 새 토큰 체계를 강요하지 않는다.
5. 라이트/다크의 실제 텍스트-배경 조합을 확인한다. 기본 목표는 WCAG AA: 일반 텍스트 4.5:1, 큰 텍스트 3:1, 해당 UI 요소는 [비텍스트 대비 기준](https://www.w3.org/TR/WCAG22/#non-text-contrast)의 3:1. 큰 텍스트 판정과 예외는 [WCAG 기준](https://www.w3.org/TR/WCAG22/#contrast-minimum)을 따른다.
6. 좁은 화면·확대·긴 문구·키보드·focus 노출·오류 복구 시나리오를 구현/QA에 넘긴다. 스크린샷만으로 접근성 통과를 선언하지 않는다.

## 산출물

[DESIGN 양식](../templates/DESIGN.md). 토큰은 대상 프로젝트 기존 형식으로 저장하며, 필요할 때만 별도 JSON을 만든다.

## 검증과 완료

화면의 모든 적용 상태가 수용 기준·데이터와 연결되는지 검사한다. 토큰 참조 유효성, 실제 대비, 인터랙션을 별개로 검증한다. 설계 완료와 구현 검증 완료를 구별한다.

## 실패·보류·사람 확인

색/데이터/브랜드 충돌은 선택안과 영향을 제시한다. 자동 검사 미지원은 수동 검증 대상으로 남긴다. 실제 사용자 수용은 사람이 판단한다.

## 다음 단계와 인계

프론트엔드에 흐름·토큰 정본·상태표, 백엔드에 필요한 데이터·오류 계약, QA에 화면별 검증 시나리오를 준다.

## 작은 작업에서 생략

기존 컴포넌트의 단일 상태 변경이면 레퍼런스 조사·새 디자인 시스템·전체 화면 재설계를 생략한다.

## 선택 검사 도구

Node가 이미 설치되어 있고 프로젝트가 3계층 JSON 토큰을 쓰면 [token-lint.mjs](token-lint.mjs)를 사용할 수 있다.

```sh
node docs/agent-kit/capabilities/token-lint.mjs --tokens docs/project/tokens.json src
```

경로는 실제 토큰 정본·소스 디렉터리로 교체한다. 실행 전 두 경로의 존재와 토큰 내용을 확인하고, 결과의 검사 파일 수가 0이면 검증 완료로 취급하지 않는다. 빈 토큰 객체도 통과할 수 있다. raw hex/primitive 직접 참조/참조 오류를 찾는 정규식 보조 검사이며 CSS 변수 해석·대비·화면 상태·접근성 통과를 보증하지 않는다. symlink가 순환하는 디렉터리 대신 명시적 소스 파일/디렉터리를 지정한다. 기존 프로젝트의 토큰 형식이 다르면 이 도구를 억지로 맞추지 말고 기존 검사를 쓴다.
