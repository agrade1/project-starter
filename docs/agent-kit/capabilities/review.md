# 독립 비평 · A/B/C · 수정 종료

## 목적과 사용 시점

기획/설계 주장 또는 구현의 반례와 안전 경계를 독립적으로 검사할 때 사용한다.

## 입력과 부족한 정보

- 필수: 요구사항·주장한 계약·원문 코드/diff 또는 설계·검증 근거·범위
- 선택: 기존 미해결 finding·재현 환경
- 부족하면: 근거를 직접 열 수 없으면 판정을 유보하고 필요한 파일/재현을 요청한다. 작성자 자기평가로 대체하지 않는다.
- 공통 경계: [작업 규칙](../common/WORKING_RULES.md). 프로젝트 경로표를 따라 기존 정본을 쓴다.

## 실행 단계

1. fresh 세션에서 읽기 전용으로 검토한다. 작성자 대화나 자기 칭찬 없이 요구사항과 실제 산출물을 직접 읽는다.
2. 승인·인증·상태 전이·데이터 손실·거짓 성공·빈 테스트·과대주장을 깨는 반례를 찾는다. 결함의 재현 조건과 근거를 적는다.
3. A: 지금 차단. 치명적 결함, 데이터 손실, 승인/인증/상태 우회, 거짓 성공·과대주장, 되돌리기 어려운 결정 또는 유예 때문에 후속 작업이 안전하지 않거나 폐기될 위험. 즉시 해결한다.
4. B: 지정 마일스톤/트리거 전 필수. 명시적 기한·담당이 있을 때만 유예한다. C: 제한된 낮은 영향의 완전성·편의·미세 개선. 대장에 남기고 기능 진행을 멈추지 않는다.
5. 심각도·확률·영향 반경·유예 비용·수정 공수·기한/트리거·담당·증거·상태를 모두 남긴다. 등급 하나만 보고 우선순위를 정하지 않는다.
6. 코드 수정 / 추가 조사 / 사람 실험·결정 / 범위 내 유예 중 해결 경로를 선택한다. 수정 검토는 finding과 영향 범위에 한정한다.

## 산출물

[REVIEW 양식](../templates/REVIEW.md). 읽기 전용 리뷰어는 응답으로 내고 기획·진행 담당이 정본에 저장한다.

## 검증과 완료

A 해결 증거를 확인하고 B/C에 담당·기한이 있어야 다음 단계로 넘긴다. 기본 수정 최대 2회 후에도 A가 남으면 미완료 인계한다. C만으로 새 리비전 루프를 시작하지 않는다.

## 실패·보류·사람 확인

반례를 못 찾았다는 것은 무결함 보증이 아니다. 미검증 범위를 명시한다. 사업 결론·실험 결과는 사람이 결정하며 리뷰어가 대신 위조하지 않는다.

## 다음 단계와 인계

구현자에게 최소 재현·수정 경계, 조사자에게 부족한 근거, 사람에게 결정/실험 요청, 기획·진행에 판정·유예 대장을 준다.

## 작은 작업에서 생략

작은 diff는 관련 코드/테스트만 검토한다. 독립성·A 경계·실제 근거는 생략하지 않는다.
