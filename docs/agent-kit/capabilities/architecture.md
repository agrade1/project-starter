# 기술 스택 · 아키텍처 · API 계약

## 목적과 사용 시점

공유 데이터/API나 되돌리기 비싼 기술 선택을 구현 전에 확정할 때 사용한다.

## 입력과 부족한 정보

- 필수: 수용 기준·기존 코드·배포 환경 제약·담당 범위
- 선택: 부하 관측·보안 요구·디자인 데이터 요구·기존 계약
- 부족하면: 실제 호출자를 찾아 미확인 가정을 표시한다. 설계와 코드가 충돌하면 구현 전 차이·영향·해결안을 보고한다.
- 공통 경계: [작업 규칙](../common/WORKING_RULES.md). 프로젝트 경로표를 따라 기존 정본을 쓴다.

## 실행 단계

1. 진입점→검증→상태 변경→응답까지 실제 흐름과 모든 호출자를 찾는다. 기존 의존성과 모듈 경계를 확인한다.
2. 현재 구조를 유지하는 최소 변경안을 우선하고 대안과 되돌릴 비용을 비교한다. 설치·새 런타임 의존성은 승인 범위를 확인한다.
3. API/함수 입력·출력·오류·인증·권한·재시도·중복 요청 의미를 예시로 정의한다. 상태 전이는 서버/공유 경계에서 검증한다.
4. 데이터 저장·마이그레이션·롤백이 필요하면 운영 영향과 사람의 실행 경계를 적는다.
5. 공유 계약과 작성자를 확정한 다음 독립 FE/BE 작업을 나눈다.

## 산출물

[TECH_PLAN 양식](../templates/TECH_PLAN.md). 기존 API 스키마가 있으면 그것을 정본으로 링크한다.

## 검증과 완료

기존 호출자·제약과 모순이 없는지, 실패·권한 경계가 테스트 가능한지 확인한다. 신규 계약은 미구현으로 표시하고 구현 뒤에 코드 일치를 검증한다. 계약 확정 전에 병렬 구현을 시작하지 않는다.

## 실패·보류·사람 확인

파괴적 데이터 변경·새 외부 서비스·되돌리기 어려운 선택은 사람의 결정이 필요하다. 모르는 부하를 근거로 분산 구조를 만들지 않는다.

## 다음 단계와 인계

작업 분해 담당에게 확정 계약·의존성·소유 파일·검증 지점을 전달한다.

## 작은 작업에서 생략

기존 함수의 작은 수정이면 영향 호출자와 검사만 기록한다. 새 아키텍처 문서는 생략한다.
