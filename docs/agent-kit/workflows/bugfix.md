# 기존 프로젝트 버그 수정·리뷰

[공통 규칙](../common/WORKING_RULES.md)과 [구현](../capabilities/implementation.md)을 따른다. 재현 없는 추정 수정, 테스트 삭제·완화, 범위 밖 정리를 하지 않는다.

| 단계·담당 | 입력 | 산출물 | 완료 조건 | 사람 확인 |
|---|---|---|---|---|
| 1 FE/BE 또는 기술 설계 | 증상·재현 입력·실제 버전/로그 | 최소 재현·기대/실제·모든 관련 호출자 | 원인 가설을 관측으로 확인 | 재현 환경·데이터 접근 부족 |
| 2 해당 구현자 | 확인한 원인·허용 파일 | 최소 원인 수정·회귀 검사 | 기존 실패가 통과하고 형제 경로도 안전 | 계약/권한/데이터 변경 필요 시 |
| 3 독립 리뷰·QA | 재현·요구사항·diff | REVIEW·실패 전/수정 후 근거 | A 해결·focused 검사·필요 사용자 흐름 | 사람 환경에서만 재현 가능할 때 |
| 4 단일 통합 담당 | 검토된 수정 | 로컬 통합·HANDOFF | 최종 상태 검사와 미검증 기록 | 운영 반영은 별도 |

리뷰만 요청됐으면 1의 자료 확인 후 3의 findings 응답에서 끝낸다. 수정 권한을 추정하지 않는다. 단일 버그에는 전체 기획·시장 조사·디자인 시스템을 실행하지 않는다.

## 리뷰 실패와 인계

| 원인 | 다음 담당·행동 | 종료·재개 조건 |
|---|---|---|
| 코드 결함 | 해당 구현자가 최소 수정 후 영향 검사 | 독립 리뷰어가 A 해결 증거 확인 |
| 근거 부족 | 리서치/기술 설계가 지정 질문만 조사 | 원문/재현 근거가 도착하면 재검토 |
| 사람 실험·결정 필요 | 기획·진행이 구체적 질문·실험·성공 기준 전달 | 실제 응답·증거가 올 때까지 해당 단계 대기 |
| 현재 범위에서 유예 가능 | B/C를 담당·기한·유예 비용과 함께 기록 | [리뷰 규칙](../capabilities/review.md)에 따라 다음 단계 진행 |

기본 수정 최대 2회. A가 남으면 미완료 인계하고 범위 축소·조사·사람 결정으로 전환한다. B/C만으로 반복하지 않는다. [HANDOFF](../templates/HANDOFF.md)로 사람이 다음 세션에 전달해도 된다. 자동 호출은 필요하지 않다.
