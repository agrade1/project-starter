# 새 서비스

[공통 규칙](../common/WORKING_RULES.md)을 적용한다. 빈 프로젝트 여부부터 확인하고 기존 코드·문서가 있으면 [기능 추가](feature.md)로 좁힌다.

| 단계·담당 | 입력 | 산출물 | 완료 조건 | 사람 확인 |
|---|---|---|---|---|
| 1 기획·진행 | 아이디어·제약·작업 범위 | PROJECT 초안·필요 역할 | 문제·범위·종료점 확인 | 조사/프로토타입/제품 개발 구분 |
| 2 리서치(필요 시) | 결정을 바꿀 질문 | RESEARCH·근거·미확인 실험 | 중요한 주장에 원문 연결 | 인터뷰·실물 검증·추가 비용 |
| 3 제품 기획 | 문제·근거·예산 | MVP/PRD·수용 기준 | 핵심 흐름·필수/제외·실험 분리 | 범위와 사업 판단·개발 승인 |
| 4 UX·UI + 기술 설계 | 확정 범위·기존 자산 | DESIGN·TECH_PLAN/API | 화면 상태와 데이터/오류 계약 일치 | 비주얼 방향·되돌리기 어려운 선택 |
| 5 기획·진행 | 확정 계약 | TASK·소유권·선행·예산 | 공유 계약 먼저 확정 | 승인 범위 증가 시만 |
| 6 FE/BE(필요한 역할만) | TASK·설계·실제 코드 | 코드·focused 검사·인계 | 수용 기준의 구현 증거 | 새 의존성·운영 영향·범위 변경 |
| 7 독립 리뷰·QA | 요구사항·diff·검사 | REVIEW·사용자 흐름 증거 | A 해결·필수 검사·B/C 기록 | 실제 사용자 수용·미검증 실험 |
| 8 단일 통합 담당·기획 | 검토된 변경 | 로컬 통합·HANDOFF | 최종 상태 검사·변경 누락 없음 | 출시는 별도 사람 절차 |

디자인/기술 조사는 입력 계약이 안정적이고 보고서 소유권이 다를 때 병렬 가능하다. 코드 병렬화는 writer별 worktree와 소유 파일을 먼저 확정한다. 서비스 전체가 작으면 1~5는 한 기획 세션, 6은 한 구현 세션으로 합친다.

## 리뷰 실패와 인계

| 원인 | 다음 담당·행동 | 종료·재개 조건 |
|---|---|---|
| 코드 결함 | 해당 구현자가 최소 수정 후 영향 검사 | 독립 리뷰어가 A 해결 증거 확인 |
| 근거 부족 | 리서치/기술 설계가 지정 질문만 조사 | 원문/재현 근거가 도착하면 재검토 |
| 사람 실험·결정 필요 | 기획·진행이 구체적 질문·실험·성공 기준 전달 | 실제 응답·증거가 올 때까지 해당 단계 대기 |
| 현재 범위에서 유예 가능 | B/C를 담당·기한·유예 비용과 함께 기록 | [리뷰 규칙](../capabilities/review.md)에 따라 다음 단계 진행 |

기본 수정 최대 2회. A가 남으면 미완료 인계하고 범위 축소·조사·사람 결정으로 전환한다. B/C만으로 반복하지 않는다. [HANDOFF](../templates/HANDOFF.md)로 사람이 다음 세션에 전달해도 된다. 자동 호출은 필요하지 않다.
