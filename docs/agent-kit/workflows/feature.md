# 기존 코드베이스에 기능 추가

기존 요구사항·디자인·코드·검사를 정본으로 사용한다. 초기화·새 스택 도입·전체 문서 재작성부터 시작하지 않는다. [공통 규칙](../common/WORKING_RULES.md) 적용.

| 단계·담당 | 입력 | 산출물 | 완료 조건 | 사람 확인 |
|---|---|---|---|---|
| 1 기획·진행 또는 구현자 | 기능 요청·기존 지침·HEAD/dirty | 현재 흐름·영향 파일 | 호출자·사용자 변경·현재 동작 파악 | 요구사항/코드 충돌 |
| 2 제품/기술/디자인 중 필요한 역할 | 변경 목표·제약 | 기존 PRD/설계의 변경 절·TASK | 포함/제외·수용 기준·소유 파일·검사 확정 | 승인 안 된 변경 범위 |
| 3 해당 구현자 | TASK·관련 계약 | 코드·focused 검사 | 정상/실패 흐름과 계약 구현 | 새 의존성·데이터/권한 확대 |
| 4 독립 리뷰·QA | 요구사항·실제 diff·검사 | REVIEW·필요 브라우저 검증 | A 해결·증거·B/C 담당/기한 | 미검증 사용자 판단 |
| 5 단일 통합 담당 | 검토된 변경·선행 증거 | 최종 로컬 상태·HANDOFF | 통합 검사·버전/변경 누락 확인 | 원격 반영·출시는 별도 |

단순 기능은 기획·진행과 구현을 같은 세션에서 역할을 바꿔 수행할 수 있다. 최종 리뷰는 독립 세션이다. 리서치·BE·worktree가 필요 없으면 생략 이유만 기록한다.

## 리뷰 실패와 인계

| 원인 | 다음 담당·행동 | 종료·재개 조건 |
|---|---|---|
| 코드 결함 | 해당 구현자가 최소 수정 후 영향 검사 | 독립 리뷰어가 A 해결 증거 확인 |
| 근거 부족 | 리서치/기술 설계가 지정 질문만 조사 | 원문/재현 근거가 도착하면 재검토 |
| 사람 실험·결정 필요 | 기획·진행이 구체적 질문·실험·성공 기준 전달 | 실제 응답·증거가 올 때까지 해당 단계 대기 |
| 현재 범위에서 유예 가능 | B/C를 담당·기한·유예 비용과 함께 기록 | [리뷰 규칙](../capabilities/review.md)에 따라 다음 단계 진행 |

기본 수정 최대 2회. A가 남으면 미완료 인계하고 범위 축소·조사·사람 결정으로 전환한다. B/C만으로 반복하지 않는다. [HANDOFF](../templates/HANDOFF.md)로 사람이 다음 세션에 전달해도 된다. 자동 호출은 필요하지 않다.
