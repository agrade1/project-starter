# 기존 코드베이스에 기능 추가

기존 요구사항·디자인·코드·검사를 정본으로 사용한다. 초기화·새 스택 도입·전체 문서 재작성부터 시작하지 않는다. [공통 규칙](../common/WORKING_RULES.md)과 [운영 모델](../common/OPERATING_MODEL.md)을 적용한다.

| 단계·담당 | 입력 | 산출물 | 완료 조건 | 사람 확인 |
|---|---|---|---|---|
| 1 기획·진행 또는 구현자 | 기능 요청·기존 지침·HEAD/dirty | 현재 흐름·영향 파일 | 호출자·사용자 변경·현재 동작 파악 | 요구사항/코드 충돌 |
| 2 제품/기술/디자인 중 필요한 역할 | 변경 목표·제약 | 기존 PRD/설계의 변경 절·TASK | 포함/제외·수용 기준·소유 파일·검사 확정 | 승인 안 된 변경 범위 |
| 3 해당 구현자 | TASK·관련 계약 | 코드·focused 검사 | 정상/실패 흐름과 계약 구현 | 새 의존성·데이터/권한 확대 |
| 4 독립 리뷰·QA | 요구사항·실제 diff·검사 | REVIEW·필요 브라우저 검증 | A 해결·증거·B/C 담당/기한 | 미검증 사용자 판단 |
| 5 단일 통합 담당 | 검토된 변경·선행 증거 | 최종 로컬 상태·HANDOFF | 통합 검사·버전/변경 누락 확인 | 원격 반영·출시는 별도 |

단순 기능은 기획·진행과 구현을 같은 세션에서 역할을 바꿔 수행할 수 있다. 최종 리뷰는 독립 세션이다. 리서치·BE·worktree가 필요 없으면 생략 이유만 기록한다.

## 리뷰 실패와 인계

[공통 루프·상태 전이](../common/OPERATING_MODEL.md)를 따른다. 결함은 작성자로, 전제/계약 오류는 기획·설계로, 근거 부족은 조사로, 사람 입력·한도 도달은 미완료 인계로 분기한다. 수정 기본 최대 2회이며 세션을 바꿔도 회차를 잇는다. 필수 기준과 A가 해결되고 B/C 담당·기한을 기록해야 완료다.
