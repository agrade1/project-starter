# 문서 연습 — 아이디어에서 첫 작업까지

가상 예약 관리 서비스 예시다. 아래 경로·요구·finding·결과는 설명용이며 실제 앱이나 사용자 실험을 실행한 기록이 아니다. 실제 프로젝트에서는 원문과 버전, 검사 결과로 교체한다.

## 입력과 첫 응답

사용자가 `docs/input/idea.md`에 “예약을 입력하고 목록에서 확인하고 싶다. 나중에는 결제와 알림도 붙인다”를 넣고, “첫 예약 등록 흐름을 로컬 프로토타입으로 구현하라. 실제 고객 데이터·결제·출시는 제외”라고 요청했다고 가정한다.

진행 담당은 원문을 보존하고 PROJECT에 다음 대응만 정리한다. 스타터 문서가 이미 있다는 이유로 기존 제품이라고 판단하지 않는다.

| 요구 ID | 원문 위치 | 해석·범위 | 수용 기준·검사 | 작업 |
|---|---|---|---|---|
| REQ-01 | idea.md 예약 입력 절·원문 버전 | 승인된 첫 흐름 | 이름·날짜 입력 → 목록 표시; 필수 값 누락 → 저장 거부 | BOOK-01 |
| REQ-02 | idea.md 목록 절·원문 버전 | 재시작 후 보존 여부는 미확인 | 로컬 메모리 데모인지 저장 기능인지 원문/사용자 확인 | BOOK-01의 가정 |
| REQ-03 | idea.md 후속 기능 절·원문 버전 | 결제·알림은 후속, 이번 제외 | 이번 완료 조건에 포함하지 않음 | 미배정 |

읽을 수 없는 원문이면 내용 추정을 멈추고 해당 입력을 blocked로 둔다. 저장 여부가 사용자 의도에 중요하면 그 질문만 전달한다. 독립적으로 가능한 입력 검증·화면 흐름 설계는 진행한다.

## 작업과 분기

BOOK-01에는 실제 환경에서 찾은 파일·기준 버전·검사 명령, 승인 범위, `blocked`(저장 범위 미확정)와 회차 `0/2`를 적는다. 공유 계약과 입력이 확인되면 `ready → running`으로 진행한다. 작은 기능이므로 worktree·그래프 파일·별도 BE 세션은 만들지 않는다.

사용자가 “새로고침 후에도 이 브라우저에서 남아야 한다”를 확정했다고 가정하면 그 승인을 REQ-02와 TASK에 반영한다. 한 흐름을 구현하고 정상 입력·누락 입력·새로고침을 실제 검사한 뒤 `review`로 넘긴다. 검사를 실행하지 못했다면 review 통과나 done으로 적지 않는다.

## 비평 입력과 개선

1차 패킷에는 REQ-01/02·원문 위치·승인된 로컬 범위·실제 관측과 미확인만 준다. 리뷰어는 산출물을 열기 전에 “등록 결과가 목록에 보이는가, 잘못된 입력을 막는가, 새로고침 후 보존되는가”를 기준으로 기록한다.

2차 패킷에는 실제 대상 파일·snapshot·diff·검사 원문을 준다. “현재 구조가 훌륭하니 완성도를 높여라” 같은 작성자 평가는 전달하지 않는다. 요약에 없는 요구가 있는지 원문도 읽는다.

가상 리뷰에서 저장이 메모리뿐인데 완료라고 보고했다면, 필수 기준 미충족과 거짓 성공을 A로 기록한다. BOOK-01은 `review → running`, 수정 회차 `1/2`. 작성자는 승인된 로컬 저장 범위에서 최소 수정하고, 새로고침 전후 검사 결과로 재검토받는다. 근거 없는 “통과” 문구 수정만으로 결함을 닫지 않는다.

반대로 저장이 필요한지조차 정해지지 않았다면 코드 패치를 반복하지 않고 기획의 범위/계약 단계로 돌아간다. 실제 고객의 재방문 효과는 이 로컬 검사로 증명하지 않는다. 알림을 추가하자는 의견은 범위 밖 제안으로 남긴다.

## 중단과 재개

2회 수정 후에도 필수 기준을 충족하지 못하면 `blocked`와 원인·필요 입력·담당·재개 조건을 남긴다. 새 모델이나 세션을 불러도 `0/2`로 되돌리지 않는다.

새 세션에는 HANDOFF의 상태·남은 회차·다음 행동과 원문/증거 경로를 넘긴다. 중간에 저장 계약이 바뀌었다면 BOOK-01 및 그 결과를 사용하는 후속 TASK/검사를 `stale`로 표시하고 영향 범위부터 대조한다. 파일 버전·검사·독립 리뷰·인계 조건이 실제 충족됐을 때만 `done`이다.
