# 문서 기반 예시 — 즐겨찾기만 보기

**가상 대상 프로젝트의 인계 연습이다.** 모델·서비스 코드·브라우저를 실행하지 않았다. 아래 프로젝트 경로·HEAD·결과는 양식을 어떻게 채우는지 보여주는 예시이며 실제 구현이나 테스트 통과 기록이 아니다.

## 상황과 승인

기존 할 일 목록에 `favorite: boolean` 값과 체크박스 컴포넌트가 있다. 사용자가 로컬 기능 추가를 승인했다. “즐겨찾기만 보기”를 켜면 즐겨찾기 항목만 보이고 끄면 전체 목록으로 돌아온다. 데이터 저장·API·정렬·다중 기기 동기화·출시는 범위 밖이다.

기준은 사람이 확인한 대상 HEAD로 채운다. 아래 예시 파일은 가상 코드 위치이며 실제 적용 시 파일을 찾아 TASK에 적는다. `docs/project/PROJECT.md`와 기존 코드가 정본, `docs/agent-kit/`은 재사용 지침이다.

| 역할 | 읽는 킷 문서 + 프로젝트 입력 | 판단·산출물 | 넘길 대상 | 실제 세션 필요 |
|---|---|---|---|---|
| 기획·진행 | [공통](../common/WORKING_RULES.md), [역할](../roles/coordinator.md), [작업 분해](../capabilities/task-planning.md), 요청·기존 문서·Git 상태 | 아래 TASK, 변경 범위·검사·기한 | 구현자·독립 리뷰 | 구현자가 먼저 이 책임을 수행해도 됨 |
| 리서치 | [역할](../roles/researcher.md), [리서치](../capabilities/research.md), 기존 사용자 요청 | 시장 조사가 결정을 바꾸지 않으므로 생략 사유 기록 | 제품 기획 | 별도 세션 생략 |
| 제품 기획 | [역할](../roles/product.md), [MVP](../capabilities/product.md), 기존 범위 | 아래 수용 기준 1~4·제외 기능 | UX·UI·구현자 | 같은 준비 세션에서 처리 가능 |
| UX·UI | [역할](../roles/designer.md), [디자인](../capabilities/design.md), 기존 checkbox/empty state | 체크박스 label·focus·빈 결과 안내; 기존 토큰 재사용 | FE·QA | 새 디자인 세션 생략 가능 |
| 기술 설계 | [역할](../roles/architect.md), [아키텍처](../capabilities/architecture.md), 기존 list selector | 기존 boolean 기준 client filter, API 변경 없음 | FE·BE 책임 확인 | 새 세션 생략 가능 |
| FE | [역할](../roles/frontend.md), [구현](../capabilities/implementation.md), [검증](../capabilities/verification.md), TASK·기존 UI | 승인 파일의 코드/검사·인계 예정 | 독립 리뷰·QA | 구현 세션 1개(실제 실행 안 함) |
| BE | [역할](../roles/backend.md), 기존 API 계약 | 서버 변경 필요 없음. 데이터 계약이 다르면 기술 설계로 되돌림 | FE·기획·진행 | 별도 세션 생략 |
| 독립 리뷰·QA | [역할](../roles/reviewer.md), [리뷰](../capabilities/review.md), [검증](../capabilities/verification.md), 요구사항·실제 diff·테스트 원문 | A/B/C와 실제 검증 결과를 반환할 예정 | 구현자·기획·진행 | 구현과 다른 fresh 세션 |

이 표는 각 역할의 연결을 점검하기 위해 전부 펼친 것이다. 실작업의 첫 프롬프트는 해당 역할만 지정하며 위 문서를 모두 한 세션에 넣지 않는다.

## 채운 작업 지시 예시

- ID: `FAV-01`
- 목표: 기존 목록에서 즐겨찾기만 필터링한다.
- 승인: 사용자 요청에 따른 로컬 UI·관련 테스트 수정. 제품 출시는 승인하지 않음.
- 입력: 실제 프로젝트 요구사항과 checkbox/list 구현, API의 favorite 타입. 없는 경로는 먼저 찾는다.
- 담당: FE 1명. 통합: 동일 구현 담당 1명. 최종 리뷰: 다른 세션.
- 기준 HEAD: 대상 프로젝트에서 확인 후 기입. 이 예시에 실제 HEAD가 없으므로 아직 착수 입력은 미완성이다.
- 소유 파일 예시: `src/features/tasks/TaskList.tsx`, 그 기능의 기존 테스트 파일. 프로젝트에 없으면 실제 경로로 교체. 공유 API/토큰 파일 변경 금지.
- worktree: 단일 writer이므로 별도 생성 불필요. 기존 dirty 파일과 겹치면 소유자를 확인하고 보존한다.
- 선행: favorite이 boolean이며 목록에 이미 포함된다는 코드 확인. 다르면 새 계약 승인 전 구현 중단.
- 시간: 준비/구현/검증 합계 60분 계획 예시. 수정 최대 2회. 추가 유료 도구 없음. 토큰은 노출된 값만 기록.
- 산출물: 소유 파일 diff, 실제 검사 결과, `docs/project/HANDOFF.md` 또는 기존 인계 문서.
- 다음: 독립 리뷰 후 A 해결·B/C 기록, 로컬 최종 검증과 인계로 종료.

수용 기준:

1. 끈 상태에서 기존 목록 전체가 기존 정렬대로 보인다.
2. 켜면 `favorite === true` 항목만 보인다. 원본 배열과 저장 데이터를 변경하지 않는다.
3. 해당 항목이 없으면 빈 결과 안내와 필터를 끌 수 있는 조작이 남는다.
4. 키보드로 켜고 끌 수 있고 label·focus가 보인다.

## 검증 계획과 정직한 인계

| 검사 | 방법 | 이 문서 연습의 상태 |
|---|---|---|
| 필터 정상/해제·원본 불변 | 대상의 기존 테스트 명령과 fixture를 확인해 실행 | 미실행 — 대상 서비스가 없음 |
| 빈 결과·키보드·focus | 실제 로컬 앱을 열고 수용 기준 3~4 수행 | 미실행 — 브라우저 테스트하지 않음 |
| 범위·API 불변 | 실제 diff와 모든 관련 호출자 읽기 | 미실행 — 코드 작성하지 않음 |
| 문서 인계 정합성 | 요구사항 → TASK → FE → 리뷰/QA → 인계 연결을 이 문서로 추적 | 수행 — 필요한 입력과 생략 역할 표시 |

리뷰에서 “검사 파일 0개인데 테스트 완료”라는 보고가 발견되는 가상 상황이라면 **A(과대주장)**다. 실제 검사를 수행하거나 보고를 미검증으로 바로잡고 완료 판정을 보류한다. “즐겨찾기 개수 배지도 추가하면 좋다”는 의견만 있다면 현재 범위 밖 C로 기록하고 반복 수정하지 않는다.

C 기록 예시(가상): 심각도 P3, 발생 확률은 현재 화면에서 항상, 영향은 편의성만, 유예 비용 낮음, 수정 공수 30분 추정, 트리거는 후속 목록 UX 개선, 담당 제품 기획, 증거는 이 예시의 추가 의견, 상태 backlog. 실제 프로젝트 finding으로 자동 등록하지 않는다.

다음 세션에는 TASK·정본 경로·실제 HEAD·승인 범위와 증거만 전달한다. 실제 작업 전에는 이 예시의 미완성 경로/HEAD를 채워야 한다. 문서 연습 완료는 기능 개발 완료가 아니다.
