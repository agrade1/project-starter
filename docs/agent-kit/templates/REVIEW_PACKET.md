# 독립 비평 입력 패킷

기존 TASK/인계 안에 아래 절을 넣어도 된다. 요약은 탐색 안내이며 원문을 대체하지 않는다. 기획·진행 담당이 준비하고 리뷰어가 사용자 원문과 대조한다. 작은 수정은 요구사항·제약·증거 경로 몇 줄이면 충분하다.

## 1차 입력 — 문제와 제약

- 리뷰 종류: 방향 비평 / 산출물 검증 / 수정 재검토
- 사용자 목표·해결할 문제 / 원문 경로·절·버전:
- 승인 범위·제외 범위 / 사용자가 고정한 제약과 승인 근거:
- 수용 기준 ID·관측 방법 / 사용자 결정과 작성자 제안의 구분:
- 관측 사실·출처 / 미확인 가정·자료 충돌·누락:
- 요청하는 판단 / 읽기 범위·도구 권한·시간/회차 한도:

fresh 리뷰어는 적용 지침과 위 문제 원문을 먼저 읽고 **판정 기준·실패 시나리오·성립해야 할 가정**을 짧게 기록한다. 방향 비평이면 현 방향 유지·더 단순한 해결·다른 접근을 어떤 증거로 비교할지도 적는다. 이미 승인된 제약을 임의로 바꾸지 않는다.

## 2차 입력 — 대상과 검증 증거

리뷰어가 기준을 기록한 뒤 이 절의 대상 파일을 연다. 단계별 전달이 가능하면 1차만 먼저 전달한다. 한 파일로 전달할 때 읽기 순서는 절차상 분리일 뿐 기술적 차단은 아니다.

- 실제 산출물 경로 / 기준 HEAD / staged·unstaged diff·untracked 파일 목록:
- 대상 snapshot 식별자(커밋 또는 파일 내용 해시/보관 diff) / 계약 버전:
- 검사 명령·환경·실제 출력 경로·대상 버전 / 미실행과 이유:
- 반대 근거·알려진 실패 / 재검토이면 finding ID·변경분·영향 범위:
- 설계 근거·결정 기록 경로(필요 시 추가 조회):

작성자의 대화·자기평가·선호안을 정답처럼 포장한 요약·이전 총점은 기본 입력에서 뺀다. 다만 요구사항·안전 제약·불리한 결과를 감추지 않는다. 처음의 기준으로 실제 산출물을 검사하고, 필요한 근거는 원문으로 추가 요청한다. 기존안 보강만이 아니라 유지·단순화·대안 전환을 비교하되 범위 밖 재설계는 제안으로 남긴다.

반환: [REVIEW](REVIEW.md)의 finding·원문 증거·해결 경로·재검토 범위. 독립 입력이 요약 편향을 완전히 없앤다고 주장하지 않는다.
