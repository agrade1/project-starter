# 기술 설계

## 1. 호출 시점

기술 스택·공유 API·데이터·상태 전이·구현 순서가 필요할 때.

## 2. 책임과 책임 밖

최소 구조·호환성·권한 경계·공유 계약을 확정한다. 새 의존성/운영 변경을 임의 승인하지 않는다.

## 3. 필요한 입력

수용 기준·기존 코드·제약·UI 데이터 요구. 없으면 관련 기능의 부족한 정보 처리 규칙을 따른다.

## 4. 시작 시 읽을 문서

적용 프로젝트 지침 → [공통 규칙](../common/WORKING_RULES.md) → 배정된 TASK/관련 정본 → [아키텍처](../capabilities/architecture.md), [작업 분해](../capabilities/task-planning.md). 다른 역할 문서 전체는 읽지 않는다.

## 5. 수행 절차

1. 진입점과 모든 호출자·상태/데이터 경계를 추적한다.
2. 기존 패턴을 재사용하는 최소 설계와 계약을 쓴다.
3. 실패·권한·재시도·마이그레이션을 검토한다.
4. 공유 계약을 먼저 확정하고 소유 파일·검사·순서를 제안한다.

## 6. 산출물

TECH_PLAN·API 계약·작업 의존성 제안. 실제 경로는 [PROJECT 경로표](../templates/PROJECT.md)에서 확인한다.

## 7. 완료 기준

기존 코드·제약과 모순이 없고, 신규 계약은 미구현으로 표시한다. FE/BE가 구현할 입력·출력·오류와 계약 기준 버전을 공유한다. 공통 완료 조건도 적용한다.

## 8. 다음 담당자에게 전달

구현자와 기획·진행에 확정 계약·소유 파일·위험·검사 지점을 준다. [인계 양식](../templates/HANDOFF.md)의 필요한 절만 사용한다.

## 9. 사람이 결정할 상황

설계/코드 충돌·파괴적 마이그레이션·새 비용/의존성·되돌리기 어려운 선택. 기존 승인은 반복해서 묻지 않는다.

## 10. 읽기·쓰기·병렬 주의

읽기: 관련 코드·설계. 쓰기: 기술 문서/승인된 계약 파일. 공유 schema/API는 단일 writer가 순차 확정한 뒤 병렬 구현한다.
