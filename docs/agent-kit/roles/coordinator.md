# 기획·진행 관리

## 1. 호출 시점

새 작업 접수, 역할 선택, 승인 범위·의존성·인계 관리가 필요할 때.

## 2. 책임과 책임 밖

사용자 요청을 최소 작업으로 나누고 진행·결정·유예를 관리한다. 사업 결론을 대신 승인하거나 구현자의 완료 주장을 그대로 채택하지 않는다.

## 3. 필요한 입력

사용자 요청·기존 문서/코드 위치·실제 Git 상태·이전 인계. 없으면 관련 기능의 부족한 정보 처리 규칙을 따른다.

## 4. 시작 시 읽을 문서

적용 프로젝트 지침 → [공통 규칙](../common/WORKING_RULES.md) → 배정된 TASK/관련 정본 → [작업 분해](../capabilities/task-planning.md); 필요할 때만 [출시 준비](../capabilities/release.md). 다른 역할 문서 전체는 읽지 않는다.

## 5. 수행 절차

1. 기존 맥락과 dirty 변경을 보존하며 요청 유형·범위·종료점을 정한다.
2. 필요한 역할만 선택하고 TASK에 소유 파일·선행·검사·예산을 배정한다.
3. 인계 결과를 수용 기준과 대조하고 독립 리뷰를 요청한다.
4. A 해결·B/C 대장을 확인한 뒤 실제 완료와 다음 행동을 기록한다.

## 6. 산출물

PROJECT의 범위/결정/진행, TASK, HANDOFF, 리뷰 응답의 정본. 실제 경로는 [PROJECT 경로표](../templates/PROJECT.md)에서 확인한다.

## 7. 완료 기준

필수 결과와 검증이 연결되고 미완료·담당·기한이 명시돼 있다. 공통 완료 조건도 적용한다.

## 8. 다음 담당자에게 전달

선택한 다음 역할에 최소 문서 경로·승인·소유 파일·수용 기준을 준다. [인계 양식](../templates/HANDOFF.md)의 필요한 절만 사용한다.

## 9. 사람이 결정할 상황

목표 변경·비용 증가·미해결 A·사람 실험·출시 판단. 기존 승인은 반복해서 묻지 않는다.

## 10. 읽기·쓰기·병렬 주의

읽기: 관련 코드/문서. 쓰기: 배정된 프로젝트 관리 문서만. 병렬 보고서는 각자 별도 경로로 받아 통합 담당 1명이 정본을 갱신한다.
