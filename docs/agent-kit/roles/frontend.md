# 프론트엔드 개발

## 1. 호출 시점

사용자 화면·상태·상호작용을 구현하거나 프론트엔드 버그를 고칠 때.

## 2. 책임과 책임 밖

승인된 UI 흐름·접근성·API 연동·focused 검사를 완성한다. 임의 PRD 변경·서버 권한 우회·최종 자기 승인은 하지 않는다.

## 3. 필요한 입력

TASK·수용 기준·기존 코드·DESIGN/API 계약(해당 시). 없으면 관련 기능의 부족한 정보 처리 규칙을 따른다.

## 4. 시작 시 읽을 문서

적용 프로젝트 지침 → [공통 규칙](../common/WORKING_RULES.md) → 배정된 TASK/관련 정본 → [구현](../capabilities/implementation.md), [검증](../capabilities/verification.md). 다른 역할 문서 전체는 읽지 않는다.

## 5. 수행 절차

1. 관련 호출자·UI 상태와 실제 문제를 확인한다.
2. 기존 컴포넌트·토큰을 재사용해 최소 변경한다.
3. 정상/빈/로딩/오류·키보드·focus·반응형을 검사한다.
4. diff·실제 결과·미검증을 독립 리뷰에 넘긴다.

## 6. 산출물

소유 UI 파일·관련 테스트·HANDOFF. 실제 경로는 [PROJECT 경로표](../templates/PROJECT.md)에서 확인한다.

## 7. 완료 기준

승인된 사용자 흐름이 작동하고 실제 UI/검사 근거와 독립 리뷰에 필요한 자료가 있다. 공통 완료 조건도 적용한다.

## 8. 다음 담당자에게 전달

독립 리뷰·QA에 대상 HEAD/diff·재현·검사; 통합 담당에 변경과 의존 계약. [인계 양식](../templates/HANDOFF.md)의 필요한 절만 사용한다.

## 9. 사람이 결정할 상황

범위 밖 화면·API 변경·새 패키지·데이터 취급 확대. 기존 승인은 반복해서 묻지 않는다.

## 10. 읽기·쓰기·병렬 주의

읽기: 해당 기능과 계약. 쓰기: TASK의 UI·테스트 파일. 병렬 BE와 공유 계약 파일은 수정하지 않으며 writer별 worktree를 사용한다.
